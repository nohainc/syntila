# Performance tests

Local latency measurements for real user actions. Nothing here touches production.

## Run

| Command | What it does |
| --- | --- |
| `scripts/perf-local.sh [--probes N] [--chats N] [--workflow chat|work] [--allow-offline] [--model ID] [--json f] [--no-thresholds]` | Full runner against `pnpm start:local`. Exit 1 when a p95 limit is exceeded or a scenario had errors. |
| `scripts/test-perf.sh` | Short run (~1 min), writes `_perf/<date>-<commit>.json`, compares each current measurement with configured limits. |
| `scripts/test-all.sh --perf` | The normal checks, then `test-perf.sh` as last step. Never runs by default. |
| `bun scripts/perf-report.mjs` | Rebuilds [PERFORMANCE_RESULTS.md](PERFORMANCE_RESULTS.md) (last 10 runs, p95 per metric). |

## Scenarios

- **A transport**: delivery probe (backend -> live Workspace Service -> backend) on the developer account's Workspace, with payloads 0, 1024 and 32768 bytes. Skipped with a warning if the Workspace is offline or its Service does not answer probes (an old Service build; restart it with the current build).
- **C workflows**: creates a temporary Space on the developer account and sends sequential Chat requests through its connected real Workspace and a ready Worker. Reports end-to-end completion time and persisted admission, service wait, delivery, and startup intervals. Defaults to one Chat request; `--chats N` controls the count and `--chats 0` skips it. Use `--workflow work` to exercise stateful Work and thread coordination. The Work benchmark creates a real Work Root directory, which can remain after the temporary Space is deleted. These requests use the configured provider and may consume quota. `SYNTILA_PERF_WORKER_ID` selects a ready Worker; otherwise ChatGPT is preferred. `--model ID` explicitly selects a model supported by that Worker. The temporary Space is deleted after terminal results and preserved on timeout. A connected real Workspace is required; failures make the run fail.
- **D real requests** (read-only): samples the last 50 requests of the developer account, including requests without assignments and multiple assignment attempts. It reports request-to-assignment admission, assignment-to-dispatch, dispatch-to-acknowledgement, start-permit-to-running, and acknowledgement-to-running. It counts requests without an assignment and assignments still awaiting dispatch or running. These persisted intervals are approximations, not measurements of the actual UI: assignment-to-dispatch can include capacity queues, and acknowledgement-to-running can include queueing. Requests without completed intervals are excluded from percentiles. The scenario is informational and has no threshold; slow admission is warned separately. Unlike C, this includes historical requests and incomplete work.

## Reading the numbers

p50 is the typical request; p95 means 95% of requests were at least this fast; p99 and max show the tail. With small samples (n < 20) p95, p99 and max are nearly the same value. Compare runs on a quiet machine; small absolute differences can be timer jitter. JSON reports mark modified working trees with `gitDirty`, so the commit alone is not mistaken for the exact code measured. A single Chat request gives one observation, not a reliable p95; increase `--chats` for a more useful sample.

## Thresholds

`scripts/perf-thresholds.json` holds p95 limits in ms. The transport limits are based on prior local measurements; real workflow limits are provisional targets chosen from observed startup times, and should be calibrated using repeated representative runs. Each metric is printed with its measured p95 and limit. Missing measurements fail unless their scenario was explicitly disabled with `--probes 0` or `--chats 0`. `--no-thresholds` reports without checking. Edit the JSON to set your own limits; provider and machine load affect results. Historical request timings are informational, not gated.

## Safety

Scenario C invokes a real provider and can consume quota. Only the local backend is used. The developer account defaults to `vitalii@nohainc.com`; set `SYNTILA_DEV_EMAIL` to choose another local account. The runner signs a local development token using the local backend key, so it does not ask for a password. Before discovering the developer Workspace, the runner verifies with a temporary synthetic user that the running backend does not update unchanged users; if that check fails, restart the local backend on the current build. Probes and their acknowledgements are held in memory on both transports; normal HTTP session and command traffic still persists independently. A temporary synthetic user is used only to verify that account discovery is safe and is removed afterwards. The benchmark Space is removed after completion or retained if work is still active. Tokens, keys and message bodies are never printed. `_perf/` is git-ignored.

## Assignment admission and acknowledgement

The gateway validates the assignment and grant, checks Service readiness and capacity, and durably marks the assignment dispatched before writing the command. On receipt, the Service validates the envelope, Workspace identity and payload, checks whether it is accepting work, and looks up the assignment journal. Existing records are handled as replays, cancellations or already-running work; a fresh assignment is recorded as `received`, checked for a handler, and recorded as `accepted`. Both journal records are flushed before the Service acknowledges acceptance. Cancellation is checked before and after journal admission. The Worker can then request a start permit and launch; an admission acknowledgement does not say that the provider is running.

The informational `assignment.validated`, `assignment.received`, `assignment.accepted` and `assignment.queued` diagnostic records describe those milestones; they do not authorize execution or provide crash recovery. They are queued without waiting for their disk writes before acknowledgement. Their files are size-bounded by log rotation, but the in-memory write queue is not bounded; events may be lost on process termination or storage failure, and sustained slow storage can grow the queue. Rejection and failure diagnostics retain their existing handling. The journal, not these diagnostics, is the recovery source; its writes remain on the acknowledgement path. Existing received-state records and replay handling remain supported.

The Service attaches monotonic admission measurements to its acknowledgement: `receiveToAckMs`, `journalLookupUs`, `receivedJournalUs`, and `acceptedJournalUs`. The latter two cover each journal operation including its lookup and durable append. The gateway emits bounded values in the `cloud_ack_received` trace with the assignment ID and transport, when both sides run versions supporting these fields. The complete `receiveToAckMs` can exceed the journal timings because it includes validation, scheduling and other Service work; the gateway-to-ack trace also includes transport. Microsecond values are Service-local elapsed durations, not cross-machine timestamps. Compare repeated real requests before and after a Workspace Service restart using the updated build; the existing database `dispatchToAcknowledgement` metric remains an approximation.

## Request admission and readiness

Readiness waiters are matched to their Work Request's primary Workspace; requests with no bound Workspace are re-evaluated on any readiness signal. Wakeups are processed in pages of 20, and an individual delivery failure does not prevent later waiters from being signaled. After registering a readiness waiter, dispatch rechecks readiness once to cover a ready signal that raced the registration. Signals only trigger re-evaluation: Workspace authorization, readiness, thread leases and atomic execution-slot admission remain authoritative. Missing or lost signals fall back to the existing timed retries.

Correlated Cloud diagnostic events record `target_selection_complete`, `assignment_preparation_complete` and `assignment_admission_transaction_complete` with elapsed milliseconds for each stage; the transaction duration includes lock acquisition and commit. `readiness_waiter_recorded`, `workspace_became_ready`, `readiness_wake_sent`, `readiness_wake_failed`, `wait_woken` and `wait_timed_out` mark the readiness and retry sequence. A wake event only proves a signal was delivered to the workflow, not that it admitted the request. Workflow replay can repeat diagnostic messages.

New assignment rows use the timestamp recorded inside the admission transaction after acquiring the account lock. The request-to-assignment metric includes prior preparation and lock waiting, but is still an approximation: it does not include transaction commit time, user interface latency, or requests without assignments. Transaction completion is separately logged. Historical rows retain their original timestamp semantics.

`--workflow work` exercises the real stateful path on a ready Workspace. To investigate readiness transitions, use a dedicated test Workspace: stop it before running `scripts/perf-local.sh --probes 0 --workflow work --allow-offline --no-thresholds`, then start it within 180 seconds after submission. Compare the readiness and retry diagnostics. The command does not stop or restart the Service, and retains its benchmark Space if the request times out. This opt-in offline path requires a ready Worker in the saved inventory and may be refused by request admission; it has not been verified against a real disconnected Service.

## Local preparation timings

For a traced assignment, `space_prepared` follows acquisition of the Space mutation lock and successful local fence preparation; the interval from `profile_ready` includes the lock wait. Stateless assignments do not emit this stage. `profile_resolved` records `mcpPreparationMs` and `remainingPreparationMs` for the execution preparation after the lock. `assignment.preparation_timing` diagnostics report MCP registry load time and each local binary verification's elapsed time, cache hit or miss, and outcome. These records omit executable paths and credentials; repeated binary events are intentionally separate. Diagnostics are best effort and are not authorization or recovery records. The cache checks file size, modification time and change time, but filesystem metadata is not a cryptographic identity and cannot establish that a file was unchanged on all filesystems.

The persisted first-permit-to-running interval includes any preparation or queueing after permit prefetch and ends when Cloud observes `running`; it is not a pure Engine or provider startup timer. Compare the first request after a service restart with subsequent requests using the local preparation timings, and treat small samples as observations rather than controlled benchmarks.

A local exploratory run on 2026-11-19 used four sequential ChatGPT Work requests on a modified working tree (`99517215d9a0`). All completed. The first local binary verification was a cache miss taking 2,664 ms; the following three were hits each recorded as 0 ms at millisecond resolution. Space lock and fence preparation took 6, 11, 13 and 4 ms. The four first-permit-to-running observations had a reported median of 466 ms and maximum of 3,179 ms. These are small, uncontrolled samples on one machine, not a general performance guarantee. The local cache's metadata limitation above still applies.

## Provider execution and result delivery

Service traces include `provider_first_output` after the Engine receives its first complete stdout line and the marker reaches the Service, `provider_last_output_reported` when stdout has drained, `provider_process_exited` after the process exits and stdout/stderr draining completes, `engine_result_received`, `service_result_persisted`, and `service_result_sending`. The last-output event is emitted at drain completion; `outputAgeMs` records the elapsed time since the last stdout line, measured by the Engine. Marker receipt also includes Engine-to-Service delivery time. It is not a model-response timestamp. A CLI may write initialization or status JSON before the model produces an answer, and quiet, failed, external or older providers may omit these markers. Service traces keep the first occurrence of each stage per assignment, so additional provider launches or retries are not separately represented. No provider output or prompt is carried in the timing markers. The Workspace requests these markers only when the Engine advertises `provider_timing_v1`; older components continue without them.

Cloud `terminal_persisted`, `workflow_observed_terminal` and `workflow_completed` mark later result handling. `workflow_completed` is emitted after the completion event is published; a polling client can observe the completed request before that marker. `scripts/latency-baseline.mjs` can correlate Cloud and Service logs by assignment/request; cross-host durations require a reliable clock offset. Local monotonic trace durations are preferable within one Service process. The performance runner observes completion through polling, so its total includes the polling interval and request/response time. The real-provider total is not a deterministic local overhead metric, and the configured 3-second threshold remains a user-defined target.

To assess startup and provider variability, run `scripts/test-perf.sh --chats 5` with `SYNTILA_PERF_WORKER_ID` and `--model ID` to fix the Worker and model. Restarting the Service provides a cold sample; subsequent requests use warm caches. These requests invoke the provider and may consume quota.
