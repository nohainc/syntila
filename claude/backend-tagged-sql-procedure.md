# Tagged SQL conversion procedure

This is a manual dry-run procedure. Do not bulk replace SQL. For each proposed file, inspect `git status` first and record the original SQL, bind order, result shape, environment/connection, transaction and effects. Inventory its `.prepare`, `.batch`, `writeAlone`, `batchAlone`, `inTransaction`, error handling and callers. Produce a reviewed diff before executing it. Keep file/area commits and run the full Phase 6 validation gate after every batch.

For a static `prepare(sql).bind(...).first<T>()` on an environment with a transaction-aware `SYNTILA_DATA`, replace with `dataOf(env).read.row<T>\`...\``. Convert each positional placeholder to its corresponding bound value, preserving repeated-parameter equality and explicit casts. Quote mixed-case aliases. For `.all<T>()`, use `.rows<T>` and replace `results` access with the returned array. For `.run()`, `run` returns a count, but compare it with adapter DML-only `meta.changes` and verify the actual command before using it. Use actual booleans and JSON values where PostgreSQL expects them, and account for the adapter's normalization before changing consumers. Read the SQL and resulting TypeScript diff side by side.

Flag for manual review rather than conversion: dynamically constructed SQL, untrusted raw fragments, batch composition or prepared statements passed elsewhere; transactions, nested joins, row or advisory locks and lock order; exception-driven control flow, SQLSTATE, constraint names and adapter-specific message text; JSON/array, bigint, boolean, binary, timestamp and alias normalization; and affected-row logic. Do not access `db.sql` for an existing transaction: use its `txEnv` and joined data. Test doubles without a PostgreSQL pool need an explicit data-layer double or real fixture.

A write outside an existing transaction requires particular care: the adapter can use a global advisory writer lock when configured, while tagged transactions do not. Preserve configured isolation and writer-lock behavior, retry boundaries, statement order, after-commit effects and metrics before conversion. Ordered batches need an atomic tagged transaction, with tested failure and rollback behavior. Map old statement labels to stable, non-sensitive tagged operation labels; verify both `server.ts` output and `scripts/backend-logs.sh` consumers. Leave any unresolved site explicit and unconverted.

For each batch: run focused tests, the full backend suite, route sweep, three serial concurrency runs (which check seeded PostgreSQL invariants), `bun run write-paths` and inspect its diff, plus monitoring checks. Count remaining `rg '\.prepare\(' src` occurrences and run the duplicate detector. Report failures and serial retries, update the status document, and commit only the owned files. Never run backend test runners concurrently: their shared cleanup can drop one another's temporary databases.
