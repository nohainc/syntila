# Tagged SQL migration: pilot and review

## Scope and decision

Use `Data` in `apps/backend/src/platform/data.ts` as the product query API. This is a staged migration: the PostgreSQL D1 adapter remains available while consumers are converted. The pilot converts only `domain/routes/profile-lab-policy.ts`, a read-only, single-row owner lookup. It uses `dataOf(env).read.row` with a bound user ID; the predicates, authorization decisions and transaction context remain unchanged. `dataOf` uses the `JoinedData` installed by `inTransaction`, so the lookup sees the current transaction's writes. Handwritten D1-only doubles cannot execute this query and must be replaced with a PostgreSQL fixture or a data-layer double; do not silently fall back to a separate connection.

## Query contract

`rows<T>` returns an array, `row<T>` the first row or null, and `run` the PostgreSQL result count (including returned SELECT rows); generic types are compile-time assertions, not runtime validation. Null remains null; undefined bindings throw. Tagged interpolations bind values, including each occurrence of a repeated input. Explicitly repeat an interpolation or use a fragment; never splice untrusted SQL into `raw`. `frag` composes query text and bindings, `list` handles supported IN and row-set forms, and `raw` is only for trusted source constants. Quote camelCase aliases: `AS "userId"`; unquoted camelCase aliases are rejected by the data layer.

The adapter and tagged API are not generally value-compatible. The adapter converts booleans to 0/1, JSON and arrays in result rows to JSON text, byte arrays to ArrayBuffer, and bigint to number without a safe-range check; tagged rows preserve booleans and parsed JSON/arrays, retain binary values, and reject bigint outside the safe-number range. Both convert dates to ISO strings. Adapter input coercion parses JSON strings for JSON columns and converts 0/1 for boolean parameters; tagged input binds actual values, so use objects/arrays for JSON and booleans for boolean columns, or explicitly cast JSON text through `::text::jsonb`. Audit every consumer and its casts; the pilot selects text fields only. Test exact affected-row counts where control flow depends on them: adapter `meta.changes` counts DML only whereas `run` uses driver count.

## Transactions and isolation

`Data.tx(label, fn)` starts a READ COMMITTED transaction, retries the whole callback at most five attempts for 40001 and 40P01, and invokes registered `afterCommit` effects once after successful commit. No network, logging with external consequences, or other irreversible effects belong in a retryable callback. Failed after-commit effects are logged, not retried. `inTransaction` creates a transaction-bound adapter and JoinedData, and nested calls join the same transaction. Pass `txEnv` throughout; outer environment operations can use another connection. Use `tx.lock(scope, id)` and row locks in account → Space → Thread → Conversation → Work Request → assignment order. Joined transactions share rollback and after-commit effects; caught SQL errors still abort the PostgreSQL transaction.

Despite the adapter method name `serializable`, its actual transaction uses the connection's READ COMMITTED default. It optionally takes the transaction-scoped global writer advisory lock when `SYNTILA_DB_WRITER_LOCK=on` (off by default in `server.ts`). Tagged transactions do not take that lock. This is a real difference when the fallback is enabled, not an isolation upgrade: do not migrate writes that depend on this serialization until their specific lock/constraint and fallback behavior are reviewed and tested. The pilot performs only a read; neither path acquires the writer lock.

D1 `batch` executes prepared statements in order on one transaction and rolls all back on error. Its tagged equivalent must be a single `Data.tx` or joined `inTransaction`, executing statements in order and collecting their results before commit; preserve row counts, first-error behavior, locks and after-commit effects. A caught failed statement cannot be followed by normal queries without a savepoint or a conflict-safe rewrite. Do not mechanically convert batches until that equivalence and the global-lock setting are reviewed.

## Errors and monitoring

The adapter wraps errors as `PgD1Error` and retains `code`, `constraint`, `table`, `detail`, `cause`, and some SQLite-style message prefixes. Tagged execution currently propagates driver errors directly (Bun exposes PostgreSQL SQLSTATE as `errno`, and `code` may be a driver code). `databaseErrorCode` in the router understands both; 23505/23503 map to 409 `conflict` and 40001/40P01/55P03 to 503 `busy`, with constraint-specific messages. Before converting an error-dependent site, verify its exact fields, constraint and message expectations, including checks for SQLite-style text; implement a common error mapping if needed. The pilot makes no error-dependent SQL decision. Do not assert complete adapter parity for errors yet.

Adapter writes record statement-derived labels in `db.writes` or `db.writer_lock`, plus `db.slow_write`; tagged transactions use explicit stable operation labels in `db.tx` and `db.slow_tx`, with count, elapsed time, retries and failures. `server.ts` drains both stat sets and `scripts/backend-logs.sh` consumes both families. Single tagged `read` statements do not produce transaction statistics; the pilot's old SELECT also produced no writer-lock statistics. For each future write conversion identify the old statement label and new stable transaction label, update dashboards/consumers if their meaning changes, and verify logging with executable tests. Never include values or personal data in labels. No production logs were accessed for this pilot.

## Review gates and open work

This pilot does not solve all adapter compatibility: fallback writer locking, adapter-normalized result values, message-dependent error handling, statement-level monitoring and ordered batches require explicit site-by-site work before broader conversion. No second domain file is authorized until design review. The full backend suite, route sweep, three serial concurrency runs, write-path regeneration and seeded PostgreSQL invariant checks form the migration gate; retain retry disclosures and compare inventory changes. Remove the runtime shim and adapter only after all product imports, tests, monitors and transaction joins are audited in Phase 7. No schema changes are proposed.
