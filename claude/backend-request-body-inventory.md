## Semantics of the helpers

`readJson` and `readBody` share the body reader (`readBodyText`: 413 over the cap, empty body = `{}`, invalid JSON = 400 `invalid_json`). `readJson` additionally requires an object (else 400 `invalid_request`). `readBody(schema)` adds schema validation and answers 400 `invalid_request` with `details: [{path, message}]`. Existing schemas use `z.object` (unknown keys stripped, not rejected) unless a handler's own code rejected unknown keys; those sites need `.strict()` to keep behavior.

## Findings to settle before Phase 2

1. **Dead handlers (sites 23, 34):** `createWorkspaceSpaceGrant` and `handleUpdateWorkspaceSpaceGrant` have no route in `routeTable()`; only unit tests call them. Decision for review: convert them (keeps tests valid) or delete them with their tests. Converting is the safe default.
2. **Silently ignored wrong types (3, 4, 25-26 partly):** the release publish handler ignores a wrong-typed `channel`, `releaseNotes`, `supportedOS` etc. and `handleRevokeWorkspaceRelease` stores a truthy non-string reason. The task wants wrong types to be 400, so these are deliberate behavior changes (admin-only routes, no repo caller).
3. **Custom error shapes the desktop client reads (30, 35-39 and 16):** the Workspace runtime and plugin routes answer `{error, code}` with codes such as `invalid_installation_id`; `readBody` answers `invalid_request` + `details`. Converting these needs a mapping that keeps their current `code`s, or the desktop client (apps/workspace, which has unrelated uncommitted edits) must change. Plan: keep the codes by catching the validation error in those handlers.
4. **Idempotency hashing (12, 14, 17, 19, 32):** `MutationIdempotency.from(..., body)` hashes the raw body. Schemas must parse for validation but the hash input must stay the raw object (or stable equivalent) so retries stay identical.
5. **Free-form candidates (allowlist):** site 1 (MCP action forwarded to the Workspace gateway) is the only payload the backend does not interpret. Everything else is structured. Site 12/9/10/11 (`WorkRequestBodySchema`) is large and shared with `createWorkRequestForUser`; its input also comes from the queue (stored JSON), so the schema must accept what the queue stores.
6. **Behavior keyed on key presence (18, 33, 27):** `handleUpdateThread` decides the permission level from the exact key set; the quota and member-access handlers require at least one key. These need `.strict()` plus a refine, not defaults.
7. **Path-dependent bodies (30):** one handler serves four paths with different bodies; it needs one schema per path.
8. **Conflict with ownership of the desktop client:** `apps/workspace/lib/workspace_cli*.dart` and `mcp_service.dart` have unrelated uncommitted edits; no Phase 2 change needs them as long as error codes are preserved (finding 3).

## Verification status of this inventory

Field lists for sites 12, 13, 18, 30, 36, 39 and 29 were checked against every `body.` read in the handler. For the others the contract was read from the validation code at the call site. Items marked "confirm at conversion" (e.g. site 13 `kind`/`ownerUserId`, site 12 which fields are client-settable) need a second read of the full handler when the schema is written, because the handler may read further fields through helper functions (`createWorkRequestForUser`, `normalizeDiscussionAttachments`, `parseWorkspaceMemberAccessPolicy`, `parseWorkflowExecutionSelection`, `validateMemberPermissions`).
